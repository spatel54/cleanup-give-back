## Patterns

- **Sessions list filter chips (`SessionsScreen`):** Selected state is primary green fill (`colors.primary`) with white `textOnPrimary` label and a matching primary border — not gray `chipSelectedBg`. Idle chips stay white fill + `borderOutline`.
- **`BrandLoadingView` is a Garbagio video overlay, not a broom sweep.** Top **75%** plays muted `assets/animations/garbagio.mp4` (`expo-video`, `contentFit="cover"` in that pane). A Welcome-style forest-green `LinearGradient` on the lower ~42% of that pane blends into the bottom **25%** message band (cream Sanchez **Saving your session. Meet our mascot, Garbagio, in the meantime!**). Clip plays **once** and pauses **2s before EOS**; `VideoView` unmounts and `garbagio-end.jpg` (frame at 6s) replaces it so native rewind to frame 0 never shows. `waitForBrandLoadingMinimum` waits for that early-stop then the overlay can go (even if save already finished). If save is still in flight, `loopWhileBusy` replays until finalize returns. Boot `preloadGarbagio` + session-end `warm` so the first frame is ready. Reduced motion shows the poster + label only. List/detail screens use inline `ActivityIndicator` + text for fetches.
- **Session-start photo Cancel returns to Session Setup** (`dismissTo('/session-setup')`), clearing pending start photos but keeping the pending form so fields rehydrate if the form remounts. Mid-session / session-end Cancel stays `dismissTo('/live-session')`. Guide **Previous** uses named `replace` helpers in `sessionSetupGuideNavigation.ts`, never bare `router.back()` after Skip/auto-skip.
- **Service Hours week nav trailing control:** On the current Monday-based week, show the Week N badge. Off that week, replace it with a quiet **This week** chip (View-backed `chipBg` fill + soft primary border + primary label — not near-white `statusApprovedBg` or full `bgTour`, which are either invisible or too loud on the white Service Hours card). Tap jumps via `goToCurrentWeek` → `applyWeekStart(startOfWeekMonday(today), today)`. Keep a small left margin so the chip does not collide with the date-range badge.
- **Service Hours calendar day cells:** In `ServiceHoursWeekPicker`, each day is a **36×36** circle (`dateCellInner`) centered in its column (`dateCell` wrapper with `flex: 1` + vertical padding). Do not stretch day backgrounds with `flex: 1` + `aspectRatio: 1` — on a 7-column grid that fills the modal width and makes adjacent week-highlight / selected disks touch. Row gap: `marginBottom: 2` on `dateRow`. Export date pickers (`ExportDateField`) still use the older full-column layout until aligned.
- **Service Hours chart layout:** Wallet-style minimal chart — no outer border, hairline horizontal grid lines at every Y tick (including **0** baseline), Y-axis ticks on the **left** in muted grey, solid primary bars (`CHART_BAR_WIDTH` 30px, 4px top radius, square bottom), wider day-column gap. Each filled bar shows an integer value inside (hours, or minutes on a sub-hour week) with no units.
- **Contribute (`DonateScreen`) keyboard layout must not grow the sticky footer inside flex.** Padding the footer with keyboard height shrinks the `ScrollView` and leaves a hollow gap between the amount card and Continue. Keep the footer absolute (`bottom: keyboardHeight` on iOS), paint a matching white filler under it to the keyboard, and scroll the custom amount field into the remaining viewport via `measureLayout` on the field wrap relative to scroll content → `scrollTo` (fallback: `scrollResponderScrollNativeHandleToKeyboard`). Do not rely on `scrollToEnd` alone — large bottom padding overshoots past the custom input. Avoid re-layout that remounts/unmounts the focused `TextInput` (that dismisses the keyboard).
- **React Compiler ("React Compiler enabled" in the Metro log) silently freezes any render-body value computed by a function with hidden, untracked dependencies** — module-level mutable state, `Date.now()`, `Math.random()`, etc. The compiler auto-memoizes render-body computations based on statically-visible inputs; a plain function call like `isCheckpointDueOrGrace()` (reads `Date.now()` + a module-level `state` singleton, no props/hooks passed in) looks like it has zero dependencies, so the compiler caches its first result **forever** and never recomputes it, even though the underlying store keeps changing. Confirmed via a temp diagnostic: `checkpointSecondsRemaining` (destructured from the `useLiveSession()` hook — a real tracked dependency) ticked down correctly every second in the logs, while `Date.now()` logged in the *same render* stayed frozen at the exact same millisecond for 30+ consecutive renders. **Fix:** any value a component needs during render that depends on wall-clock time or external mutable state must be computed inside the store (e.g. on each tick in `syncSessionClocks()`) and exposed as a field on the reactive `LiveSessionState`/`useLiveSession()` snapshot — never called as a "pure-looking" imperative function directly in a render body. Calling the same functions inside `useEffect` bodies, `setInterval`/`setTimeout` callbacks, or event handlers is safe — the compiler only memoizes render-body computations, not imperative code that runs after render. `checkpointDueOrGrace` and `checkpointOverdueSeconds` in `liveSessionStore.ts` are the reference example of the correct pattern; audit any *new* direct call to `isCheckpointMissed`/`isCheckpointInGracePeriod`/`getGraceSecondsRemaining`/`hasSubmittedCheckpointForCurrentWindow` (etc.) placed directly in a component's render body against this trap before shipping.
- **`PhotoEnlargeModal` re-seeds safe area inside RN `Modal`.** `Modal` hosts a separate native window, so parent `SafeAreaProvider` insets often read as `0` and chrome slides under the status bar / home indicator. Wrap modal content in `<SafeAreaProvider initialMetrics={initialWindowMetrics}>` before `SafeAreaView`.
- **`FeedbackScreen`'s chat-bubble typing dots grow left-to-right** (small → medium → big) toward the bubble's tail. Figma `1126:1554` specced the mirror (big → medium → small, shrinking toward the tail) and an earlier session matched that spec, but explicit user feedback reversed it back to small → medium → big — treat this as the current intentional direction, not a regression, if revisiting. Fade-in stagger must also fade one dot in *before* the next starts (`BUBBLE_STAGGER_MS` > `BUBBLE_TIMING.duration`) — equal/overlapping timings read as "all at once" even though each dot animates independently.
- Use Figma design tokens from `frontend/src/constants/tokens.ts` (or feature re-exports). `theme.ts` chrome colors/fonts/spacing are wired to those tokens.
- **Button radius tiers (DS §7):** `radius.sm` (8px) — inputs and inline action buttons paired with inputs or dense bulk bars (e.g. Membership **Apply**, Sessions/Letters export bars). `radius.md` (16px) — cards, full-width primary/secondary CTAs (`EmptyState`, onboarding footers, `SessionButton`, Account Pay/Log Out, shop **Continue**). `radius.full` — chips (filters, status tags, role tags, type chips), pills, FABs, and circular icon buttons. Do not use `radius.md` on input rows.
- **Profile photo editor:** `ProfilePhotoCropModal` is full-screen over Account — circular crop frame, pan/pinch, **Fill** (cover) vs **Crop** (cover + slight zoom) presets; confirm exports via `cropProfilePhoto.ts` then `profilePhoto.ts` uploads.
- Prefer `ThemedView` for light/dark chrome; for product copy prefer `AppText` / `textStyles` over `ThemedText` or ad-hoc font sizes
- **Photo-capture zoom labels are optical, not a linear 0–1 map.** Driven by `resolveZoomPlan` (`lib/cameraZoom.ts`): with an optical ultra-wide, 0.5×→1× is a real crop into the wide lens; without one (every front camera, single-lens backs), 0.5× and 1× stay at the sensor's full frame (anchor `1`, no digital crop) and above 1× zooms in. Selfie locks to that full frame with **no zoom UI**; rear keeps the multi-scale dial. Do not pass the dial’s 0–1 value straight into `CameraView`.
- **The absolute `zoomFactor` prop (real 1×/3× accuracy) only works on a custom dev client or a real native build — never on Expo Go.** Expo Go is a fixed prebuilt binary and can never include `patches/expo-camera+57.0.4.patch`'s native `zoomFactor`/`onAvailableLensesChanged` additions; on Expo Go, `resolveZoomPlan` silently falls back to the approximate `factorToNativeZoom` curve. When a local EAS build reports `patched YES` but the fallback curve values still show up, check whether `expo-modules-autolinking`'s precompiled-modules feature swapped `expo-camera` for a prebuilt XCFramework instead of compiling the patched source — confirm via `strings` on the built binary for `switchOverFactors`/`constituentDeviceTypes`, and set `EXPO_USE_PRECOMPILED_MODULES=0` in the build profile's `env` (see `eas.json`) if so.
- **Crossing the optical hand-off point (e.g. 0.5×→1× onto the wide lens) is animated with `device.ramp(toVideoZoomFactor:withRate:)` in the patch, not an instant `videoZoomFactor` snap** — matches the stock Camera app's smooth pinch-zoom feel and gives auto-exposure time to settle. `PhotoCaptureScreen`'s `SequentialCapture` additionally fires a brief dark flash (`lensCrossingFlash`, via `crossesLensBoundary` in `lib/cameraZoom.ts`) whenever the requested zoom crosses one of the device's `switchOverFactors`, masking the framing jump — the ultra-wide lens sits at a different physical position on the camera module than the wide/telephoto pair, so switching to/from it visibly shifts the frame (parallax); this is real optics, not something fixable purely via `zoomFactor`, and it does not occur on the wide↔telephoto hand-off (those lenses are nearly co-located).
- **Photo Retake (`PhotoCaptureScreen`):** Do not slide full-screen preview/camera layers — remounting `CameraView` mid-translate looks janky. Cross-fade on a black host: keep preview on top while mounting capture underneath at opacity 0, fade preview out (opacity + slight scale), then fade camera in after a short head start. Respect `useReducedMotion()` with an instant swap.
- **Native-only modules need a `.web.tsx` stub, not a runtime `Platform.OS` check.** `@maplibre/maplibre-react-native`'s components call `codegenNativeComponent`, which `react-native-web` doesn't implement — the crash happens at *module-evaluation* time (when the file is `import`ed), before any `Platform.OS` branch in the importing code ever runs. Metro's platform-extension resolution (`.web.tsx` beats `.tsx` on web) is the only way to keep the native module out of the web bundle entirely. `ui/map.web.tsx` follows the existing `animated-icon.web.tsx` precedent: same exported API surface, inert implementation. Consumers (e.g. `features/session-tracking/components/LiveSessionMap.tsx`) still do their own `Platform.OS === 'web'` check so they can render a styled fallback instead of nothing.
- **Never write `el.style.transform` on a MapLibre GL JS marker's root element** (the element passed to `new maplibregl.Marker({ element })` in `webViewMapHelpers.ts`). MapLibre owns that CSS property to translate the marker to its screen position on every `setLngLat`/pan/zoom, and will silently overwrite anything else written there — so setting a rotation directly on the root element causes it to snap to the container's top-left corner after the next map update (visible as the marker appearing, then jumping, on load or `setMapStyle`). Rotate an inner wrapper `<div>` instead (see `createArrowMarkerElement`/`updateArrowMarkerElement`), leaving MapLibre's root-element transform untouched.
- **Both `LiveSessionMapWebView.tsx` and `SessionRouteMapPreviewWebView.tsx` observe their `#map` container with a `ResizeObserver` and call `map.resize()` on change** (plus on `orientationchange`). MapLibre GL caches its canvas pixel size at construction time and never recomputes it on its own; the RN `WebView`'s container settles to its final layout size a beat after the HTML first runs, and physically rotating/moving the phone can resize it again. Without a `resize()` call, `map.project()` keeps using the stale size, so every marker (start, current-position, end/tip) visually drifts away from its true screen position. Any new WebView MapLibre instance in this feature needs the same observer wiring.
- **Event location pin previews use Carto Voyager *raster* tiles, not the vector GL style URL.** The vector style (`…/voyager-gl-style/style.json`) paints its cream background (`#fbf8f3`) even when `tiles-*.basemaps.cartocdn.com` MVTs fail (ad blockers, srcDoc iframe quirks), which looks like a blank map with only the HTML pin. `EventLocationMapWebView` and web-app `EventLocationMap` inline a raster style pointing at `a–d.basemaps.cartocdn.com/rastertiles/voyager/…`. Live session maps keep the richer vector style.
- **Don't gate a post-`setStyle` marker resync on `map.isStyleLoaded()`.** `LiveSessionMapWebView.tsx`'s `window.setMapStyle` (used by the live map-theme sun/moon toggle and layer switches) keeps the current-position Marker DOM attached across `map.setStyle(...)`, then re-syncs overlays once `map.once('style.load', ...)` fires. `'style.load'` only means the new style document (fetched from Carto's remote Voyager URL, or applied inline from the locally-patched Dark Matter JSON in `mapStyles.ts`) has been parsed and applied — `isStyleLoaded()` can still read `false` for a beat afterward while sources/tiles catch up. `applyRouteOverlay`'s regular `isStyleLoaded()` guard, if left in place for that resync call, silently skips `syncMarkers()` and leaves the tip gone until the next GPS fix. Fixed by adding a `forceApply` param so the post-style-swap resync bypasses the guard (the `'style.load'` event already proves it's safe); the regular GPS-driven `window.updateRoute` path keeps the guard. Live tracker does **not** draw a gray start pin (native or WebView) — only the green heading tip — so short walks don't look like a black duplicate beside the tip.
- **Live maps draw `appendLiveTipToDisplayRoute(displayRouteCoordinates, displayCoordinate)`** so the polyline reaches the EMA-smoothed arrow between ~1m GPS appends; stored `routeCoordinates` for finalize are unchanged. Tip append requires ≥2 committed route points — a single GPS seed never invents a seed→pin segment (standing still stays marker-only).
- **Live tracker maps must not mount until a GPS center exists.** `LiveSessionMapNative` / `LiveSessionMapWebView` show a surface spinner until `getLiveSessionMapCenter()` returns a fix. `startLocationWatching` starts `watchPositionAsync` (and compass) immediately after foreground permission, then seeds last-known / timed Balanced `getCurrentPositionAsync` (8s cap) in parallel — never await an untimed one-shot or Always permission before the watch, or a hang leaves the map spinner forever. Never fall back to continental US (`DEFAULT_MAP_CENTER` / zoom 3–4) on the live tracker.

- **Recent Cleanups tiles use a static raster snapshot, not live MapLibre.** `ImpactFeedSection` renders `SessionMapSnapshot` (CARTO Voyager `{z}/{x}/{y}@2x` via `expo-image` + SVG path, keyed through `cartoBasemap.ts`) from persisted `mapAnchor`. CARTO raster tiles without `EXPO_PUBLIC_CARTO_BASEMAP_API_KEY` show a "KEY REQUIRED" watermark — set the free key from https://carto.com/basemaps/apikey in `frontend/.env` and EAS production env. Do not remount `SessionRouteMapPreview` / WebView maps in the feed — empty `routePreview` plus `DEFAULT_MAP_CENTER` is what produced the US-center bug. No GPS (`mapAnchor == null`) → neutral brand surface.
- **Your Impact month/year picker is list-only and activity-filtered** — `ImpactFeedSection` opens a bottom sheet with a scrollable month or year list from `buildActiveImpactYearOptions` / `buildActiveImpactMonthOptionsForYear` (session activity plus current year/month as a floor). Volunteers tap a row to select. Do not re-add a type-to-search `TextInput` / **Go** row or a 100-year calendar span unless product explicitly asks.
- **`transparentModal` Expo Router screens pushed on top of each other must be dismissed with `router.dismissTo(...)`, not `router.replace(...)`, when finishing the chain.** `PhotoCheckpointScreen` ("Photo required") pushes `/photo-capture` on top of itself rather than replacing, and its own auto-dismiss effect is guarded to only fire while it's the *focused* screen — so once `/photo-capture` is pushed, that guard permanently blocks `PhotoCheckpointScreen` from popping itself. `PhotoCaptureScreen`'s submit handler used to `router.replace('/photo-submitted')`, which only swapped out `/photo-capture`, leaving `/photo-checkpoint` mounted underneath the new `/photo-submitted` transparent modal (both visible/overlapping). Fixed by using `router.dismissTo('/photo-submitted')`, which pops every intervening screen (React Navigation's `POP_TO`, which pushes the target fresh if it isn't already in the stack) before showing the target.
- **A missed photo checkpoint no longer pauses tracking or force-ends the session** — that mechanism (`forcedEndPending`/`isForcedEndPending` in `liveSessionStore.ts`) was removed; a missed window just stays open/overdue until the volunteer submits a photo (see `recordCheckpointMissIfNeeded`'s comment). Any UI or notification copy claiming the session will "pause" or be "forced to end" for a missed checkpoint is stale — `checkpointNotifications.ts`'s grace reminders were rewritten to a neutral nudge for this reason.

## Policies

- Follow [brand.md](../brand.md) for colors and fonts
- **The tracker's dark map style (`cartoDarkMatterStyle.json` + `buildCartoDarkMatterStyle()` in `mapStyles.ts`) is a local snapshot of Carto Dark Matter, not a live URL.** Upstream Dark Matter paints `landcover` (wood/grass/recreation_ground), `park_national_park`, and `park_nature_reserve` the same near-black (`#0e0e0e`) as the background, making parks/nature reserves/green landcover invisible; MapLibre's React Native wrapper has no `setPaintProperty`-style hook to patch this post-load, so the fix vendors the style's `layers` array locally (sources/sprite/glyphs still point at Carto's CDN) and repaints those layers a legible dark green (`#1f3d2a` fill / `#7fae8f` `poi_park` label text) at module load. If Carto changes upstream Dark Matter, re-fetch `https://basemaps.cartocdn.com/gl/dark-matter-gl-style/style.json` and refresh the local copy — the greenspace layer IDs may need re-checking.
- **Carto's vector `park` source-layer (both Dark Matter and Voyager) only ships a `fill` layer for `class == national_park` and `class == nature_reserve`.** Named local parks (e.g. Devonshire Park) come through as `class == "park"` and get no polygon fill at all in the stock style — only a `poi_park` point label — so they read as basically absent on the map, independent of theme. `buildCartoDarkMatterStyle()` inserts a synthetic `park_local` fill layer (same `park_nature_reserve`-adjacent position in the layer stack, filtered to exclude `national_park`/`nature_reserve` so it doesn't double-paint) to cover this gap for dark mode. Voyager (light) was left as-is since only dark mode was reported as hard to read — if that gap needs fixing too, mirror `park_local` into a light-mode style override rather than assuming Carto will ever ship it upstream.
- New shared UI goes here; screen-specific UI stays in route files or `frontend/prototype/screens/`
